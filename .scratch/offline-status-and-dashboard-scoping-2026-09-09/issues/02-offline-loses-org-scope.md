# 02 — Offline loses track of the active organisation

Status: ready-for-agent
Blocked by: None — can start immediately
Category: bug

Source: Field App testing, 2026-09-09, Joe — "When offline, app seems to lose scope of which
organisation you've selected (both on main call to action page and settings page)."

## Agent Brief

**Category:** bug (missing offline cache — same class already solved twice elsewhere)

**Summary:** Both `Home.razor` (ticket 05 of the previous round) and `Settings.razor`'s existing
"Active location" section call `IUserLocationClient.GetMyOrgsAsync()` to find the active org, and
that method requires a live API call — `UserLocationClient.GetMyOrgsAsync`
(`src/DotGlasses.App/Auth/UserLocationClient.cs:24-37`) explicitly catches every failure
("Unreachable, offline, or the token has expired") and returns `[]`. Offline, that's every call,
every time: Home falls back to showing no org name at all, and Settings shows "No locations
assigned yet — contact your admin" — which reads as if the technician has been unassigned, not
merely offline.

This is the same gap `ReferenceDataClient` (`src/DotGlasses.App/ReferenceData/ReferenceDataClient.cs`)
and `AuthTokenStore` (`src/DotGlasses.App/Auth/AuthTokenStore.cs`) already solved for reference
data and the JWT respectively: **write-through to IndexedDB on a successful load, fall back to the
last-cached copy on failure.** The org list has never gotten the same treatment.

**Desired behavior:** The active org's name stays visible on both Home and Settings while offline,
using whatever was last successfully fetched — same "log in once online, work offline after that"
promise the token and reference data already keep.

**Key interfaces:**
- `src/DotGlasses.App/Auth/UserLocationClient.cs` — add the same write-through/fallback pattern
  `ReferenceDataClient.LoadAsync`/`WriteCacheAsync`/`TryLoadFromCacheAsync`
  (`src/DotGlasses.App/ReferenceData/ReferenceDataClient.cs:53-94`) already uses: on a successful
  `GetMyOrgsAsync`, serialize the result to `dotGlassesIdb.kvSet` under a new storage key (e.g.
  `"my-orgs-cache"`, following `AuthTokenStore`'s `"auth-token"` / `ReferenceDataClient`'s
  `"reference-data-cache"` naming); on failure, fall back to `dotGlassesIdb.kvGet` for that key
  before returning `[]`.
- `src/DotGlasses.App/Pages/Home.razor` and `src/DotGlasses.App/Pages/Settings.razor` — no change
  needed beyond what already calls `GetMyOrgsAsync`, once the client itself caches — both screens
  already consume whatever the client returns.
- `Settings.razor`'s `SwitchLocationAsync` (`Settings.razor:117-136`) is already blocked by
  `disabled="@(org.IsActive || _switchingOrg || _unsentCount > 0)"` on the button and by
  `SwitchOrgAsync` itself needing a live `switch-org` POST — switching location already correctly
  requires connectivity (per CLAUDE.md's "Location switching only works online" known-accepted-risk
  entry) and should stay that way; this ticket is only about *displaying* the already-known active
  org while offline, not about enabling offline switching.

**Acceptance criteria:**
- [ ] After at least one successful online load, going offline and reloading (or navigating to)
      Home still shows the correct active org name.
- [ ] Same for Settings' "Active location" section — the previously-active org still shows as
      selected (✓) while offline, not "No locations assigned yet."
- [ ] A device that has *never* been online still shows the same honest "no cached copy yet"
      degradation `ReferenceDataClient` already uses for its own first-run case, not a misleading
      "no locations assigned."
- [ ] Once back online, a fresh `GetMyOrgsAsync` call overwrites the cache as normal — no stale
      data lingers after a real org reassignment.

**Out of scope:**
- Enabling offline location *switching* — deliberately stays online-only (see Key interfaces).
- Any change to `ReferenceDataClient`/`AuthTokenStore` themselves — this ticket only extends the
  same already-established pattern to a third client.
