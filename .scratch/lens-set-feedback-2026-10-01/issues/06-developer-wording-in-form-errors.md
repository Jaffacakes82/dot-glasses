# 06 — Form errors a technician sees are written for developers

**Status:** ready-for-agent
**Category:** bug
**Blocked by:** None — can start immediately (touches the same form as 05; land 05 first if both are in flight)

> *This was generated by AI during triage.*

Reported 2026-10-01: leaving "Reason not purchased" blank on a Lead shows a message that names the
request field and a "reference-data item" rather than saying what to do. About twenty messages in
the shared consultation rules are written the same way (required dropdowns, "Other" free text, the
referral fields, "'Full Name' must not be empty").

Decision (2026-10-01): make as many of them human-readable as is appropriate, now, rather than
waiting for the map's user-facing wording ticket (`ceo-feedback-2026-09-27` ticket 22). That ticket
still owns labels, headings and terminology; this one owns only error messages.

## Agent Brief

**Category:** bug
**Summary:** Every consultation rule message a person can cause from a form says, in plain words,
what to do.

**Current behavior:**
`ConsultationRules` (and the lens power rules it calls) report many failures in developer terms:
property names, enum names, "reference-data item", "must be empty when X is false", and
FluentValidation's generated copy ("'Full Name' must not be empty.").

**Desired behavior:**
- A message a technician or admin can trigger through a control names the control by its on-screen
  label and says what to do: "Choose a reason not purchased.", "Enter the customer's full name.",
  "Say what the other reason is.", "Enter a phone number.", "Age must be between … and …".
- No message shown against a control contains a DTO property name, an enum member name, or the
  words "reference-data".
- The same message is used wherever the rule runs — Field App pre-submit check, API response,
  Failed records, and the Admin Portal's lead conversion — because they share the one rule.
  Wording must therefore read correctly on both forms.
- Messages that can only arise from a malformed request no form can produce (an empty record Id,
  fields the forms defensively blank) may stay technical; list which were left and why in the PR.
- Failure **keys** do not change — they are the request property names and the forms attribute by
  them.
- Messages already written plainly (lens choice, lens-set availability, current location) are
  left alone.

**Key interfaces:**
- `ConsultationRules` and `LensPowerRules` — message strings only.
- Tests that pin message text — updated to the new copy; this is a deliberate client-visible
  change, so call it out in the PR description.

**Acceptance criteria:**
- [ ] Saving a Lead with no reason shows a plain instruction against "Reason not purchased".
- [ ] Each required field left blank on the Test, Lead and Sale forms shows a plain instruction.
- [ ] No message reachable from a form control contains a property name, enum name or "reference-data".
- [ ] No failure key changes; server and device still produce identical text for the same failure.
- [ ] The PR lists every message changed (old → new) and every technical message deliberately kept.

**Out of scope:**
- Labels, headings and other non-error wording (map ticket 22).
- Admin Portal validators outside the consultation rules.
- When errors appear or clear — ticket 05.
