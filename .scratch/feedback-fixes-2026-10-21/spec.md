# Spec G — Fixes from the 21 October feedback

**Status:** ready-for-agent
**Source:** [CEO feedback, 21 Oct 2026](../ceo-feedback-2026-10-21/map.md), tickets 01, 06, 08, 11,
14, 15, 16, 17 and 18. Each ticket's Agent Brief has the detail behind the decisions here.

> *This was generated by AI from the triage of the 21 Oct feedback.*

## Problem Statement

The CEO tried both apps on a phone and hit a run of problems that don't need a product decision:

- The installed Field App, refreshed with no connection, shows the browser's own "You're offline"
  page and never starts. That is the one thing it must never do.
- Forms start with answers already chosen (Gender "Female", Outcome "No glasses needed"), so a
  technician who skips a question saves a plausible-looking wrong answer.
- A lens that comes in only one coating still makes the technician tick it, and the Sale is
  refused until they do.
- Coatings sit below the children's frame and pupil distance questions, away from the lens they
  belong to.
- Cancelling a part-filled form asks through a browser pop-up headed with the site's address.
- On the Admin Portal, the Organisations screen is unusable on a phone. The User Directory
  repeats an "Outside your scope" chip for every hidden assignment, and lists a well-connected
  user's organisations down most of a screen.
- The Dashboard's gender split counts Tests. DGI wants the split of the people who buy.

## Solution

- The installed Field App opens and refreshes offline, on any page, once it has been online
  once.
- Every required choice on the Field App's forms starts blank and must be answered.
- When the chosen lens offers exactly one coating and a Coating set is being asked for, that
  coating is ticked for the technician. This applies on the Field App and on the Admin Portal's
  lead conversion, through one shared rule.
- Coatings come straight after the lens on every form.
- Leaving a part-filled form asks in the app's own dialog, with no site address.
- The Organisations screen stacks on a phone, with nothing scrolling sideways.
- The User Directory lists only the organisations the viewer can see, and folds long lists
  behind a "+N more" control.
- The Dashboard's gender split counts Sales and says so.

## User Stories

**Working offline**

1. As a technician, I want the installed Field App to open with no signal after I've used it
   online once, so that I can record in a clinic with no connection.
2. As a technician, I want to refresh the app offline without it getting stuck on "You're
   offline", so that a refresh never costs me the rest of the day's work.
3. As a technician, I want a refresh on a form page or the Failed records page to load offline
   too, so that it doesn't matter which page I was on.
4. As a technician, I want the app to work offline after a new release once I've opened it
   online once since, so that an update never strands me.
5. As a technician, I want the app's own offline banner and behaviour after an offline refresh,
   so that I know my records are being kept for later.

**Choosing answers deliberately**

6. As a technician, I want Gender to start blank on a new Test, Lead and Sale, so that I can't
   save the wrong gender by skipping it.
7. As a technician, I want Outcome to start blank on a new Test, so that a customer who needs
   glasses isn't recorded as not needing them by default.
8. As a technician, I want a clear message on Gender if I save without choosing one ("Choose a
   gender."), so that I know what to fix.
9. As a technician, I want a clear message on Outcome if I save without choosing one ("Choose an

10. As a technician, I want the "Needs glasses" questions to stay hidden until I choose that

14. As a technician, I want to be asked before leaving a form where I've only chosen a gender or

## Implementation Decisions

**Offline start (ticket 16)**

- Diagnose before fixing, with `/diagnosing-bugs`. "You're offline" is Chrome's fallback page for
  an installed web app: it shows when the service worker doesn't answer a page request. The fix
  goes where the cause is: the published service worker's install, its page-request fallback,
  or the app's start-up path. The PR names the cause and how it was confirmed.
- Every page request the app owns is answered with the cached app shell, deep links included.
  The cache is still versioned by the build's asset manifest, so a new release replaces it.
- No change to the outbox, `ISyncService` or how reference data is cached (`ReferenceDataClient`,
  `FramePictureCache`).

**Answers that start blank (ticket 15)**

- On the consultation form, the Gender and Outcome form state becomes nullable and starts empty,
  with a "Select…" placeholder. The request DTOs don't change: a blank never reaches the server,
  because the form checks it before queuing. The server already refuses an out-of-range value.
- The pre-submit checks add two `FormErrors` entries, keyed on the request properties `Gender`
  and `Outcome`. The messages are "Choose a gender." and "Choose an outcome.", in the established
  voice: a plain instruction naming the control by its on-screen label. No `ConsultationRules`
  message changes.
- Seeding is unchanged. A Lead continued from a Test, a Sale converted from a Lead (via
  `SaleAssembly.Seed` at load time) and a Failed record opened for fixing all start with their
  carried answers.
- The unsaved-data check counts a chosen Gender or Outcome as entered data.
- No other control is pre-chosen. Frame coverage is not shown on the form, so it keeps its fixed
  value. The Admin Portal's conversion form doesn't ask Gender or Outcome, because identity comes
  from the Lead.

**Coatings: auto-tick and position (tickets 18 and 14)**

- The Field App's coating reconcile function (`CoatingSelection.Reconcile`) moves into `Rules`
  beside `PairedCoatings`. `App` may reference `Rules`, and nothing in the function needs more.
  The Field App and the Admin Portal then share one tested function.
- The moved function gains one rule: **when a Coating set is being asked for and exactly one
  coating is offered, that coating is ticked.** The caller says whether a Coating set is being
  asked for. It is on a Sale, and on a Lead only when it orders. It is not when only a Coating
  preference is asked for, nor when the set is locked from an ordered Lead. The rule applies when
  the offered coatings are reconciled (a lens chosen or changed, or a record loaded). It does not
  reapply after the technician unticks the coating, so unticking stays possible and gives the
  usual error.
- Custom (and no range) offers every active coating, as today. With exactly one active coating
  the same rule ticks it.
- On the Admin Portal, the conversion form's coatings endpoint (the one the form calls when the
  chosen lenses change) adds an `autoTicked` value: the coating the Rules function would tick,
  or none. The conversion script ticks it. The script still holds no coating rule of its own.
- Order of the lens section on every form (Test with "Needs glasses", Lead, Sale, and the Admin
  Portal's conversion): lens range → lens (or custom powers) → power line → **coatings** →
  children's frame → pupil distance → order from DOT Glasses. On a Sale, frame colour and hard
  case keep their place in the Sale details. Only positions change: no control, rule or message
  changes. This replaces the order decided in the 27 Sep round's ticket 10. Add a line to that
  ticket's answer saying so.

**Discard dialog (ticket 17)**

- A small in-app confirmation dialog replaces the browser `confirm()` on the consultation form's
  back/cancel path. It uses the design tokens and the existing `dg-*` button classes. "Keep
  editing" is the default and is also what Escape does. "Discard" leaves the form.
- It is a reusable component, so later confirmations can use it too. Settings' and No location's
  inline sign-out confirmations stay as they are.
- No `confirm()` or `alert()` call remains in the Field App.

**Organisations on a phone (ticket 11)**

- The tree/detail layout moves from an inline two-column grid to a `dg-*` layout class in the
  Admin Portal's design-system stylesheet. It is two columns above the existing mobile
  breakpoint, and stacked (tree, then detail) below it.
- Choosing an organisation on a phone brings its detail panel into view by anchoring to it. No
  new script is needed if the selection is already a link.
- The design tokens are hand-kept in both `Web` and `App`. This change adds a layout class, not a
  token, so only the Admin Portal's stylesheet changes.

**User Directory (tickets 06 and 08)**

- `UserAdminService`'s directory listing stops adding an "Outside your scope" placeholder for
  hidden assignments. Each row carries only the names of organisations in the viewer's scope.
  The Edit user page's hidden-organisation count (`OutsideScopeCount`) is unchanged.
- In the list, the first two organisations show as chips. A user with more gets a native
  disclosure element (`<details>`/`<summary>`) labelled "+N more" that opens the rest in place,
  per row. It needs no script, so the full list is always reachable. The order is the service's
  existing order.
- The empty state for a user with no assignment at all (listed for DGI-level callers only) is
  unchanged.

**Dashboard gender split (ticket 01)**

- `DashboardCalculator` works out the male/female split from the Sales it's given, not the
  Tests. The query service already loads Sales under the same filters and the same training-org
  exclusion. Nothing new is loaded.
- The result's field names stay. The card's label becomes "Gender split (sales)".

**No schema, API or migration changes.** The only contract change is the extra `autoTicked`
value on the Admin Portal's conversion coatings endpoint. It is internal to that screen.

## Testing Decisions

- **What a good test is here:** it checks behaviour someone can observe, such as a figure, a
  rendered page, a JSON response, or what a pure rule returns for given inputs. Never which
  private method ran. Admin Portal tests assert on rendered HTML and endpoint responses through
  the real host, against the containerised Postgres, as the existing screen tests do.
- **Application.Tests, `DashboardCalculator`:** a case where Tests and Sales have different
  gender mixes shows the Sales mix. A range with no Sales gives the empty split. Prior art: the
  existing dashboard calculator tests.
- **Rules.Tests, the moved reconcile function:** the existing behaviour moves with it unchanged:
  offered ticks kept, others removed and reported, pairings applied. New cases for the auto-tick
  rule:
  - one coating offered, nothing ticked, Coating set asked for: it is ticked;
  - the same with the set not asked for: nothing is ticked;
  - two or more offered: the selection is unchanged;
  - one offered and already ticked: no duplicate;
  - one offered that is a pairing trigger: its pair is ticked too.

  Prior art: the paired-coatings and lens-set lenses tests.
- **Web.Tests, Admin Portal screens:**
  - The User Directory list contains no "Outside your scope" text and shows only in-scope chips
    for a user with assignments both inside and outside the viewer's scope. The Edit page still
    shows the hidden count. Prior art: the user directory scope tests and the edit user tests.
  - A user with more than two organisations renders two chips and a "+2 more"-style disclosure
    containing the rest.
  - The conversion form renders the coating control before the children's frame and pupil
    distance controls. Prior art: the lead conversion lens section tests.
  - The conversion coatings endpoint returns `autoTicked` for a lens pair offering one coating,
    and none for a pair offering two or more. Prior art: the lens-set test data and coating API
    tests.
  - The Dashboard renders "Gender split (sales)". Prior art: the dashboard screen tests.
- **By hand on staging, as in earlier rounds** (the Field App has no test project, and a new one
  was considered and turned down). A browser checklist recorded in the PR:
  - offline open and refresh on the home page, a form and Failed records, on an installed
    Android app in flight mode;
  - blank Gender and Outcome, and their messages;
  - continued, converted and Failed-record forms still pre-filled;
  - coatings directly under the lens on all three forms;
  - one-coating lens auto-ticked on a Sale and an ordering Lead, and not on a non-ordering Lead;
  - the discard dialog: keep editing, discard, untouched form;
  - the Organisations screen and Add sub-organisation dialog at 375×812;
  - "+N more" expanding in the User Directory.
