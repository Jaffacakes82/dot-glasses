# 07 — Referral question redesign

Source: Admin & App Feedback, 2026-08-10, "On the Admin"

Referrals should become a separate follow-up question, asked consistently:

- Someone can be referred in every outcome (buy / don't buy / lead / not a lead / no need for
  glasses) — the referral question should appear as a follow-up on all relevant pages, not be
  tied to one particular outcome.
- No preset answer; most people are not referred, so it should default to "off" and be quick to
  toggle — possibly a checkbox.
- Add an "other" referral-reason option with free text.
- Add a "treated in facility" follow-up checkbox that, when checked, removes/hides the referral
  location field — some facilities have their own general doctors or eye professionals who can
  treat in-house rather than referring out.
- Rename the field/language from "Referred" to "Referred or treated" to account for internal
  treatment as well as external referral.

Category candidate: enhancement, design-heavy (touches Test/Lead/Sale forms and likely the
`ReferenceDataCategory` for referral reasons) — route to grill-with-docs once triaged.

## Settled design (post-grilling, 2026-09-03)

**Baseline facts** (as of grilling): referral is Test-only today, tied exclusively to
`TestOutcome.Referred`. `Lead`/`Sale` have no referral fields. The "other reason" free-text ask
is already fully implemented (`ReferralReason` category already has an active `IsOtherOption`
item, and `ReferenceDataDropdown` already reveals free text generically) — no work needed there.
"Treated in facility" is entirely new. Test/Lead/Sale are create-once with no update endpoint,
which shapes everything below. This feature has not shipped, so no live/historical data needs
preserving — implement clean, no legacy shims.

**Architecture**
- Remove `TestOutcome.Referred` outright (no `[Obsolete]` shim, no backfill migration — nothing
  live depends on it). `TestOutcome` stays a 2-value enum (`NoGlassesNeeded`/`NeedsGlasses`) —
  don't collapse it to a bool.
- "Referred or treated" becomes an orthogonal concept, independently captured on each of `Test`,
  `Lead`, and `Sale` at creation time (no update endpoint exists, so nothing can be retrofitted
  after the fact).
- The checkbox appears **unconditionally** on all three consultation forms — not gated on which
  outcome/result is being recorded.
- It's expected and acceptable that the same real-world referral could be independently
  (re)recorded at more than one stage of a converting journey (Test → Lead → Sale), since state
  never carries forward automatically between the three create-once entities.

**New schema — identical shape added to `Test`, `Lead`, and `Sale`:**
- `ReferredOrTreated` (`bool`, default `false`) — explicit toggle state, not inferred from
  reason-non-null
- `ReferralReasonRefId` (`Guid?`) — FK into the existing, shared, non-hierarchy-scoped
  `ReferenceDataCategory.ReferralReason` list (reused as-is across all three entities)
- `ReferralOtherText` (`string?`)
- `ReferralLocationFreeText` (`string?`)
- `TreatedInFacility` (`bool`, default `false`)

Matching properties added to `CreateLeadRequest`/`CreateSaleRequest` (mirroring the existing
`CreateTestRequest` shape), each with its own independent FluentValidation validator per this
repo's no-cross-project-DTO-sharing convention (`Contracts` can't reference `Domain`/
`Application`).

**UI behavior** (`ConsultationForm.razor`, all three `Type` branches):
`[ ] Referred or treated` (default off) → reveals *Reason for referral/treatment* (dropdown +
existing Other free-text support, required) → nested `[ ] Treated in facility`, which when
checked hides only the *Referral location* free-text field. The reason stays required either
way — treated-in-facility only suppresses location, per the ticket's literal wording.

**Naming**
"Referred or treated" is a **UI-copy-only** rename. Underlying C# property names, enum members,
and DB column names keep the existing "Referral"/"Referred" naming — no functional benefit to
renaming identifiers, and unnecessary churn in a public repo.

**Reporting**
Event History must surface the referred/treated indicator for `Test`, `Lead`, *and* `Sale` rows
(today it's Test-only). No legacy/backward-compat display handling needed — this hasn't shipped.
