# 05 — Lens-coating compatibility rules

Source: Admin & App Feedback, 2026-08-10, "Field Distribution App"

Several related points about preset-catalogue and custom-lens coating selection:

- In preset catalogues, only the coatings actually configured for a chosen lens should be
  selectable; every other coating option should be non-selectable. For custom lenses, all
  coatings and lens types should remain available.
- Some coatings should default-pair: selecting "blue block" should auto-select "photochromic",
  but the reverse (photochromic → blue block) should NOT auto-select. More pairings like this
  are expected in future.
- Some coatings are mutually exclusive: "clear" excludes photochromic and sunglasses;
  photochromic and sunglasses also exclude each other.
- Add "anti-glare" as a coating type in reference data (reviewer notes admins could add it
  themselves via Reference Data, but flags it in case rule 1 above makes that harder).
- Coating should become a compulsory question in the consultation flow.

This is the single largest design item in the feedback — likely needs a `/grilling` session of
its own (rule precedence, how pairing/exclusion rules are modelled/configured, whether this
lives in `LensStrengthCoatingOption` or needs a new construct) before it's agent-ready.

## Agent Brief

**Category:** enhancement
**Summary:** Coating becomes a set of independently-selectable reference items per lens, with
admin-configurable pairing (auto-add) and exclusion (mutually-incompatible) rules between them

**Current behavior:**
A Sale's lens carries a single Coating reference — one dropdown, one value (Lead has a looser,
optional "coating preference" equivalent). Preset ranges already restrict that single choice to
whichever coatings are configured as available for the chosen lens strength; custom lenses
already allow any active Coating. Coating is already a required field on Sale, for both preset
and custom.

**Desired behavior:**
A lens's Coating becomes a *set* of active Coating reference items rather than a single value —
a lens can carry more than one coating at once (e.g. Blue Block + Photochromic together). Two new
kinds of admin-configurable relationship exist between Coating reference items:

- **Pairing** (directional): selecting Coating A automatically adds Coating B to the set as a
  default. The reverse does not automatically apply. The technician can still manually remove the
  auto-added coating afterward; later removing the triggering coating does not remove the
  paired-in one.
- **Exclusion** (symmetric): Coating A and Coating B can never both be present in the same lens's
  set. A selection that would put two mutually-excluded coatings into the set at once is blocked,
  with an inline explanation of which coatings conflict — never silently resolved by removing
  something already selected.

These relationships are properties of the coatings themselves, universal across preset and
custom lenses alike — a separate concern from the existing per-catalogue "which coatings are
available for this lens strength" restriction, which is unchanged and still narrows the *choices
offered* on a preset lens; pairing/exclusion govern which *combinations* are valid once a choice
is available, on preset or custom.

Both relationship types are managed by DGI admins from the existing Reference Data screen's
Coating category — editing a Coating item lets an admin specify which other active Coatings it
pairs with and which it excludes. Saving a rule that would directly contradict an existing rule
of the other kind between the same two coatings (a pairing where an exclusion already exists, or
vice versa) must be rejected at save time with a clear validation error, not allowed to reach
consultation-time.

A new "Anti-glare" Coating reference item should be added as seed data, with no pairing/exclusion
rules of its own.

Sale's coating requirement stays compulsory — now interpreted as "at least one coating in the
set" rather than "a non-null single value." Lead's coating field is unchanged: optional, and not
in scope for this work.

**Key interfaces:**
- Coating on a Sale (and wherever else a single coating reference currently represents "the
  lens's coating") needs to become a collection of Coating references rather than a single value.
- A new relationship construct between Coating reference items, capturing both pairing
  (directional) and exclusion (symmetric) — distinct from the existing LensStrength↔Coating
  availability relationship, which is unrelated to this work and stays as-is.
- The Reference Data screen's Coating category management UI needs to expose editing these
  relationships against other active Coating items.
- Validation (client- and server-side) needs to: block a selection that would violate an
  exclusion, apply a pairing's default add when its trigger is selected, and reject a saved rule
  that contradicts an existing rule of the other kind.

**Acceptance criteria:**
- [x] A Sale's lens can have more than one Coating selected at once.
- [x] Selecting a Coating with a pairing rule automatically adds the paired Coating to the set;
      the technician can still uncheck the auto-added Coating afterward without it being
      re-added.
- [x] Unchecking the Coating that triggered a pairing does not remove the coating it had
      auto-added.
- [x] Attempting to add a Coating that would violate an exclusion with an already-selected
      Coating is blocked, with an inline message naming the conflicting coatings.
- [x] Preset lenses still only offer coatings configured as available for the chosen lens
      strength (existing restriction, unchanged); within that offered set, pairing/exclusion
      rules still apply.
- [x] Custom lenses still offer any active Coating (existing behavior, unchanged); pairing/
      exclusion rules apply there too.
- [x] A Sale still requires at least one Coating selected, for both preset and custom lenses.
- [x] DGI admins can define and edit pairing and exclusion relationships between active Coating
      items from the Reference Data screen's Coating category.
- [x] Saving a pairing rule that contradicts an existing exclusion between the same two coatings
      (or vice versa) is rejected with a clear validation error.
- [x] A new "Anti-glare" Coating reference item exists, seeded, with no pairing/exclusion rules
      attached.

**Out of scope:**
- Any change to Lead's coating field — it remains optional and untouched by this work.
- Any change to the existing per-catalogue coating-availability restriction — unchanged, still
  preset-only.
- A richer conflict-resolution UI beyond blocking with an explanatory message (e.g. suggesting
  which existing selection to remove) — only if it turns out to be trivial alongside the above.
