# 03 — No application logs reach the Container App's log stream in nonprod

Status: ready-for-agent
Blocked by: None — can start immediately
Category: bug

Source: Field App non-prod testing, 2026-09-09, Joe — "I'm not seeing any application logs at all
in my backend application in my non-prod Azure env."

## Agent Brief

**Category:** bug (observability gap)

**Summary:** `DotGlasses.Web`'s `Program.cs:28-31` wires up Serilog (`builder.Host.UseSerilog(...)`)
but configures **zero sinks** — no `Serilog:WriteTo` section exists in `appsettings.json` or any
environment-specific appsettings file (verified: none of them contain a `Serilog` key at all), and
no `.WriteTo.Xyz()` call appears in code either. `ReadFrom.Configuration` finds nothing to read,
`ReadFrom.Services` only wires enrichers/DI, not sinks. With no sink configured, Serilog silently
drops every log event — nothing reaches stdout, so nothing reaches the Container App's console log
stream (`az containerapp logs show --type console`), which is what non-prod's log visibility
depends on.

**This is very likely why the JWT-signing-key exception that broke Field App login earlier
today never appeared when checking container logs during that investigation** — same root cause
(nothing was ever being written), different symptom, being tracked here as a defect in its own
right rather than folded into the login-fix commit.

Separately, `ServiceDefaults/Extensions.cs:47-53` also registers OpenTelemetry as a logging
provider via `builder.Logging.AddOpenTelemetry(...)`, but that pipeline only actually exports
anywhere if `OTEL_EXPORTER_OTLP_ENDPOINT` is set (`AddOpenTelemetryExporters`,
`Extensions.cs:81-98`), which it isn't in nonprod today (`docs/open-issues.md`'s "Azure Monitor /
Application Insights exporter connection string isn't configured anywhere" — a separately tracked,
larger piece of work). Fixing that is out of scope here; this ticket is specifically about
restoring the baseline "the container's own stdout has the app's logs" capability, which needs no
Azure resource provisioning.

**Current behavior:**
Nothing written by `ILogger`/`Log.*` calls anywhere in `DotGlasses.Web` appears in
`az containerapp logs show --name ca-dotglasses-nonprod --resource-group rg-dotglasses-nonprod
--type console`.

**Desired behavior:**
Serilog writes structured logs to the console (stdout), so Container Apps' native console log
stream shows them — including unhandled-exception logging from
`DomainRuleViolationFilter`/the default ASP.NET Core exception-handling middleware, and Serilog's
own request-logging if added later.

**Key interfaces:**
- `src/DotGlasses.Web/Program.cs:28-31` (`UseSerilog` configuration — add `.WriteTo.Console(...)`,
  most likely with `Serilog.Formatting.Compact`'s `CompactJsonFormatter` or similar so Log
  Analytics/Container Apps' structured log ingestion parses it well; a plain `WriteTo.Console()`
  is an acceptable minimal fix if compact JSON isn't already a project dependency)
- Check `DotGlasses.Web.csproj` for whether `Serilog.Sinks.Console` (and optionally
  `Serilog.Formatting.Compact`) is already referenced; add the package reference if not.

**Acceptance criteria:**
- [ ] After deploying, `az containerapp logs show --name ca-dotglasses-nonprod --resource-group
      rg-dotglasses-nonprod --type console --follow` shows request/lifecycle log lines during
      normal use.
- [ ] Deliberately triggering a server error (e.g. hitting an endpoint that throws) produces a
      visible Error-level log line in that same stream.
- [ ] Local `dotnet run` still shows console output as it does today (no regression to local dev
      logging).

**Out of scope:**
- Wiring an actual OTLP/Azure Monitor exporter, or setting `OTEL_EXPORTER_OTLP_ENDPOINT` /
  `APPLICATIONINSIGHTS_CONNECTION_STRING` — that's the separately-tracked, larger observability
  item in `docs/open-issues.md`. This ticket only restores stdout/console visibility.
- Any change to log *levels* or *content* beyond making the existing pipeline actually emit
  somewhere.
