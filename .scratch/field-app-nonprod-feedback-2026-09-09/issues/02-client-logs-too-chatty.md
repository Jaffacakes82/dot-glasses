# 02 — `client-logs` ships every framework Information log, not just app warnings/errors

Status: done (implemented 2026-09-09, PR: fix/field-app-nonprod-feedback-2026-09-09)
Blocked by: None — can start immediately
Category: bug

Source: Field App non-prod testing, 2026-09-09, Joe — "The client-logs seems to generate a log
for absolutely everything. It feels far too chatty. For example, it generated 2,400 unsynced
events in the space of minutes."

## Agent Brief

**Category:** bug (over-logging / possible feedback loop)

**Summary:** `BatchingLogger.IsEnabled` (`src/DotGlasses.App/Logging/BatchingLoggerProvider.cs:65`)
enables any log at `LogLevel.Information` or above, from **any** category — it applies no filter
by category at all. This class is registered as a global `ILoggerProvider`
(`Program.cs:38-39`), so it captures every `ILogger<T>` call across the whole app, including
framework-internal logging that was never meant to be a "client log."

**Current behavior:**
Verified live against the deployed nonprod Field App: a single login POST alone produces four
Information-level log lines from the `HttpClient` logging handler (`Start processing HTTP
request`, `Sending HTTP request`, `Received HTTP response headers`, `End processing HTTP
request` — category `System.Net.Http.HttpClient.Api.*`), all of which `BatchingLoggerProvider`
captures and queues as `ClientLogEntryDto` batches
(`FlushThreshold = 20`, `BatchingLoggerProvider.cs:16`). A grep of the entire `DotGlasses.App`
project found exactly two explicit application log calls anywhere —
`SyncService.cs:71` and `:76`, both `LogWarning` — meaning **100% of the "Information" volume
being shipped is framework noise**, not the "warnings, errors, key lifecycle events" the class's
own doc comment (`BatchingLoggerProvider.cs:8-13`) says it's for.

This is also plausibly self-amplifying: syncing a client-log batch is itself an HTTP POST through
the same logged `HttpClient`, which emits four more Information log lines about *that* request,
which get captured and queued for the next flush — a loop that runs regardless of user activity
and fully explains "2,400 events in minutes."

**Desired behavior:**
`BatchingLogger.IsEnabled` only captures `LogLevel.Warning` and above. This matches what the class
already claims to be for, and matches everything the app itself currently logs (its two calls are
both `LogWarning`). If a genuine need for a deliberate Information-level "key lifecycle event" log
shows up later, that's new scope — introduce an explicit opt-in at that point rather than
widening the blanket capture back out.

**Key interfaces:**
- `src/DotGlasses.App/Logging/BatchingLoggerProvider.cs:65` (`BatchingLogger.IsEnabled`)

**Acceptance criteria:**
- [ ] `IsEnabled` returns `false` for `LogLevel.Information` and below; `true` for `Warning` and
      above (excluding `None`, as today).
- [ ] `SyncService`'s two existing `LogWarning` calls (sync failures) still reach `client-logs`.
- [ ] Normal app usage (login, navigation, a sync cycle) does not produce a large burst of queued
      client-log entries — spot-check the outbox count before/after a few minutes of idle
      `ConnectivitySyncTrigger` polling.

**Out of scope:**
- Adding per-category allow/deny filtering (e.g. explicitly excluding `System.Net.Http.*`) — the
  level-based fix already removes 100% of the currently-observed noise, so the extra complexity
  isn't warranted unless a future deliberate Information-level log reintroduces the problem.
- Changing `FlushThreshold` or the sync retry policy (`Deferred` = retry indefinitely) — those are
  working as designed once the volume problem above is fixed.
