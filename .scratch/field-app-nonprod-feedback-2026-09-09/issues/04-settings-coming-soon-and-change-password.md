# 04 — Settings: drop the "Coming soon" placeholders, add a real Change Password action

## Agent Brief

**Category:** feature (new endpoint + UI) with a cleanup (dead placeholder removal)

**Summary:** `Settings.razor`'s "Toolkit" section (lines 44-50) renders three hardcoded,
permanently-disabled items ("Talking points & FAQs", "Near-vision chart", "Distance-vision chart",
each suffixed "· Coming soon") with no way to ever become real from this screen. There is also no
Change Password action anywhere in the Field App — no API endpoint exists for it today; the only
existing `ChangePasswordAsync` usage is the Admin Portal's cookie-based
`AccountController.ChangePassword` (`src/DotGlasses.Web/Controllers/AccountController.cs:131`),
which isn't reachable from a JWT-authenticated API client.

**Current behavior:**
- `Settings.razor:44-50` always renders the three "Coming soon" Toolkit rows, unconditionally,
  with `cursor:default` — pure dead UI.
- No `POST api/v1/auth/change-password` (or equivalent) endpoint exists on `AuthController`.

**Desired behavior:**
- Remove the "Toolkit" section (`_toolkitItems` field and its render block) entirely — no
  "coming soon" placeholders anywhere on the screen.
- Add a real Change Password action: a small form (current password, new password) that posts to
  a new JWT-authenticated endpoint and shows success/failure inline, following the same
  inline-message pattern already used elsewhere on this screen (`_message`/`_locationError`).

**Key interfaces:**
- `src/DotGlasses.App/Pages/Settings.razor:44-50` (Toolkit section to delete)
- `src/DotGlasses.Web/Controllers/Api/V1/AuthController.cs` — add a new `[HttpPost("change-password")]`
  action, following the existing `Login`/`SwitchOrg` pattern: resolve the current user via
  `ICurrentUserContext`/`UserManager`, call
  `userManager.ChangePasswordAsync(user, currentPassword, newPassword)`, check the
  `IdentityResult` (don't assume success — see `AccountController.ChangePassword:131-148` for the
  exact pattern including error handling), return `Ok()`/`ValidationProblem()` accordingly. A
  fresh JWT is **not** needed afterward — password changes don't alter any JWT claim, and (per
  `SwitchOrg`'s own doc comment) there's no server-side token revocation to invalidate the old one
  either way, so nothing regresses by leaving the current token as-is.
- New `Contracts.Auth.ChangePasswordRequest` DTO (`CurrentPassword`, `NewPassword`) — add
  validation consistent with the existing Identity password policy
  (`RequireNonAlphanumeric`/`RequireUppercase`/`RequiredLength = 8`, set in `Program.cs:82-84`)
  the same way `LoginRequest`'s validator already handles its own rules (per CLAUDE.md: there's no
  general request validator pattern here — see how `AuthController`'s existing actions call an
  `IValidator<T>` directly).
- New client method on `App/Auth` (e.g. extend `IUserLocationClient` or add a small dedicated
  client) posting to the new endpoint, wired into `Settings.razor`.

**Acceptance criteria:**
- [ ] Settings no longer shows any "Coming soon" item.
- [ ] Settings has a Change Password form; a correct current password + a new password meeting the
      policy succeeds and shows a success message.
- [ ] A wrong current password, or a new password that fails the policy, shows a clear inline
      error and does not change the password.
- [ ] The existing session (JWT) keeps working immediately after a successful change — no forced
      re-login.

**Out of scope:**
- Building out the actual Toolkit features (FAQ/vision charts) — the ask was to remove the
  placeholders, not implement the real thing.
- Any change to the Active Location section — already working, not part of this report.
