## Agent Brief

**Category:** bug (misleading UI copy / stale doc comments)

**Summary:** The User Directory invite/reset banner unconditionally claims "No email sending is
wired up yet," but in any environment where Azure Communication Services is provisioned (this
non-prod environment included, per `CLAUDE.md`'s Deployment section), real email *is* sent —
which is exactly what the reporter observed. Two code comments make the same now-incorrect claim.

**Current behavior:**
- `Views/UserDirectory/Index.cshtml:18-24` always renders: *"No email sending is wired up yet —
  copy this set-password link and send it to `{email}` yourself"* whenever `TempData["SetPasswordLink"]`
  is set — i.e. after every Invite/Reset action, regardless of whether `AzureEmailSender` actually
  ran and whether it succeeded.
- `UserDirectoryController.Invite`/`ResetPassword`
  (`src/DotGlasses.Web/Controllers/UserDirectoryController.cs:55-63`, `:65-83`) call
  `emailSender.SendPasswordSetupInviteAsync(...)` — real delivery via ACS when provisioned
  (`src/DotGlasses.Infrastructure/Notifications/AzureEmailSender.cs`), a logging stub otherwise
  (`LoggingEmailSender`) — but the view has no way to know which one ran, and the copy assumes the
  stub unconditionally.
- The class-level doc comments on `AccountController`
  (`src/DotGlasses.Web/Controllers/AccountController.cs:9-14`, "no email sending yet (IEmailSender
  is stubbed)") and `IEmailSender`
  (`src/DotGlasses.Application/Notifications/IEmailSender.cs:3-6`, "Real delivery ... is not
  implemented yet") are the same stale claim, left over from before `AzureEmailSender` was added.
  `docs/functional-capabilities.md:400-404` already documents the real, current behavior correctly
  — these two comments just weren't updated alongside it.

**Desired behavior:**
- The on-screen banner no longer makes an unconditional "not wired up" claim. The set-password
  link must still always be shown (per `docs/functional-capabilities.md:403-404`, it's the
  deliberate fallback for delivery failure, not just the pre-ACS era) — reword it to something
  accurate in both cases, e.g. "An email was sent to `{email}` if delivery is configured in this
  environment — you can also copy this set-password link and send it yourself:". Do not attempt to
  report back real delivery success/failure per-request (`AzureEmailSender` deliberately never
  throws back to the controller — see its own doc comment — so the controller has no signal to
  pass through).
- Update the two stale doc comments (`AccountController.cs:9-14`, `IEmailSender.cs:3-6`) to
  reflect that `AzureEmailSender` is the real implementation, wired whenever ACS is provisioned
  (deployed environments), with `LoggingEmailSender` as the local-dev/unprovisioned fallback.

**Key interfaces:**
- `src/DotGlasses.Web/Views/UserDirectory/Index.cshtml:18-24`
- `src/DotGlasses.Web/Controllers/AccountController.cs:9-14` (doc comment only)
- `src/DotGlasses.Application/Notifications/IEmailSender.cs:3-6` (doc comment only)

**Acceptance criteria:**
- [ ] The User Directory banner no longer claims email is "not wired up" unconditionally.
- [ ] The set-password link is still always shown in the banner (fallback preserved).
- [ ] `AccountController`'s and `IEmailSender`'s doc comments accurately describe the current
      `AzureEmailSender`/`LoggingEmailSender` split instead of claiming email is stubbed/not
      implemented.

**Out of scope:**
- Making `AzureEmailSender` report delivery success/failure back to the controller/view — it's
  deliberately fire-and-forget per its own doc comment, and changing that is a bigger change than
  this copy fix.
- Any change to `LoggingEmailSender` or local dev behavior.
