# 03 — Why AspNetUsers carries HierarchyPath as well as OrgNodeId

Status: wontfix (question answered, no defect found)
Blocked by: None
Category: question

Source: Joe, 2026-09-26. "Hierarchy path is stored in AspNetUsers and OrganisationNodes, even
though AspNetUsers has an OrgNodeId link to the OrganisationNode table — why do we need it in
both? And should OrgNodeId be a foreign key?"

## Answer

**Should `OrgNodeId` be a foreign key?** It already is.
`ApplicationUserConfiguration` adds `FK_AspNetUsers_OrganisationNodes_OrgNodeId` (nullable,
`Restrict`). The migration `20260910071312_AddUserOrgAssignmentForeignKeys` added it and first
cleaned up orphaned rows. It shipped in `9231e01`. **Caveat:** that deploy run reached staging,
but the production job is still waiting on the approval gate (since 2026-09-10). If you were
looking at the production DB, the constraint isn't there yet.

**Why the path is copied onto the user:** it is a deliberate denormalised cache of
`OrganisationNodes.HierarchyPath` (with `OrgLevel` alongside it for the same reason). Three
readers use it:

1. **Sign-in claims.** `ApplicationUserClaimsPrincipalFactory` writes `user.HierarchyPath` straight
   onto the `HierarchyPath` claim. From then on, every request's data scoping (the global EF query
   filter) and RBAC (`OrgLevelRequirement`) read the claim, with no DB round trip.
2. **User Directory scoping.** `ApplicationUser` is an Identity type outside the automatic
   hierarchy filter, so `UserAdminService` applies `u.HierarchyPath.StartsWith(prefix)` by hand
   (CLAUDE.md, "Data scoping vs RBAC"). With the path on the row, that is a single-table prefix
   query.
3. **Resource-based authorization** for user write actions (`Users.ManageInScope`) checks the
   target user's path.

The same pattern is used on `Tests`/`Leads`/`Sales`/`Customers`, and there it is essential: the
query filter is a `StartsWith` on the row's own column.

**Is the duplication risky?** Only if the two copies can drift. A node's path never changes after
it is minted (there is no "move org" feature), and a user's copy is written in one place, when
the assignment changes (`UserOrgAssignmentService`, `UserAdminService.InviteAsync`). So the cache
is stable. Both of the gaps found so far (`d86f986`, `9231e01`) were about the *assignment*
(`OrgNodeId` vs `UserOrgAssignments`), not about the path drifting.

**Recommendation: keep it.** Removing it means the claims factory and User Directory join to
`OrganisationNodes`, plus a migration, and the only gain is dropping one sync obligation that is
already centralised. Revisit only if a "move an org under a different parent" feature is ever
built. That would rewrite paths, and then *every* stamped copy (users *and* events) must be
rewritten together, the same job ticket 02 does by hand.
