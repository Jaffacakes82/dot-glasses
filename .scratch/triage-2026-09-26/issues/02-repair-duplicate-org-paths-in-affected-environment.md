Until this is done, the Dashboard, Event History and Custom Orders return 500 for **every** user
in the affected environment. All three build an `OrgTreeLookup` over the whole unscoped org tree,
so one duplicate anywhere takes them down for everyone, not just users under `/1/2/`.

## Needs info from reporter

1. **Which environment?** Staging/nonprod, production, or a local DB?
2. **Output of the diagnostic below**, which confirms the mechanism in 01 and sizes the repair.

```sql
-- Every node sharing a path with another, active or not. A duplicate between an active and a
-- deactivated node is latent: reactivating the deactivated one crashes the dashboard again.
SELECT "HierarchyPath", "Id", "Name", "Level", "ParentId", "IsDeleted",
       "CreatedAtUtc", "CreatedBy", "DeletedAtUtc", "ModifiedAtUtc", "ModifiedBy"
FROM "OrganisationNodes"
WHERE "HierarchyPath" IN (
    SELECT "HierarchyPath" FROM "OrganisationNodes" GROUP BY "HierarchyPath" HAVING COUNT(*) > 1)
ORDER BY "HierarchyPath", "CreatedAtUtc";

-- How much data is stamped on each colliding path (repair size)
SELECT p.path,
  (SELECT COUNT(*) FROM "Tests"       WHERE "HierarchyPath" = p.path) AS tests,
  (SELECT COUNT(*) FROM "Leads"       WHERE "HierarchyPath" = p.path) AS leads,
  (SELECT COUNT(*) FROM "Sales"       WHERE "HierarchyPath" = p.path) AS sales,
  (SELECT COUNT(*) FROM "Customers"   WHERE "HierarchyPath" = p.path) AS customers,
  (SELECT COUNT(*) FROM "AspNetUsers" WHERE "HierarchyPath" = p.path) AS users
FROM (SELECT DISTINCT "HierarchyPath" AS path FROM "OrganisationNodes"
      GROUP BY "HierarchyPath" HAVING COUNT(*) > 1) p;
```

What the output tells us: if seeded Kenya (`a0000000-0000-0000-0000-000000000002`) shows a
`ModifiedAtUtc` after a deactivation, it was reactivated over a re-minted path. If two
non-seeded rows share a name with near-identical `CreatedAtUtc`, a create was double-submitted.
Either way the fix in 01 is the same.

## Repair outline (to firm up once the above is known)

Keep the **older** node on its path. Move the newer node and its whole subtree onto fresh
segments, i.e. rewrite its `HierarchyPath` prefix. Every table that stamps a copy of the path
must be updated in the **same transaction**:

- `OrganisationNodes` — the moved node and every descendant (prefix rewrite).
- `AspNetUsers.HierarchyPath` — users whose `OrgNodeId` is in the moved subtree (join on
  `OrgNodeId`, not on the path, because the path is ambiguous).
- `Tests` / `Leads` / `Sales` / `Customers` — **the hard part.** Rows stamped with a colliding
  path are ambiguous by construction. Best available disambiguator: `TechnicianUserId` → the
  user's org assignment. For nonprod test data, "reassign by technician, accept imperfection" is
  probably fine. For production it needs a human decision per row set.

After the repair: already-issued JWTs (the Field App keeps its token in IndexedDB) still carry the
old path claim until they expire or the user signs in again. Affected technicians should sign
out and back in *after* their outbox is empty, or they will keep stamping the old path.

Why `ready-for-human`, not `-agent`: it needs direct write access to a deployed Entra-auth Postgres
(CLAUDE.md: nothing runs against a real environment from a developer machine except through the
sanctioned path), and the attribution of ambiguous rows is a judgement call. If this is nonprod
and the data is disposable, an alternative is to deactivate one of the two duplicate subtrees
*and* renumber it, so 01's unique index can still be created.
