# 09 — Refuse a lens set that isn't available at the record's location

Status: done (implemented 2026-09-26, branch feat/lens-sets)
Blocked by: 07 (rewrites the same lens-range rule branch)
Category: bug

Source: grilling of ticket 04, 2026-09-26, Joe (Q6, Q14). See ADR-0005.

## Agent Brief

**Category:** bug

**Summary:** A Test, Lead or Sale may only name a lens set that reaches its location: active,
and assigned at or above the record's org. Today the server accepts any `PresetCatalogueId` at
all, so "only the lens sets assigned to my scope" is enforced only by what the Field App happens
to display.

**Current behavior:**
`ConsultationRules`' preset branch (`Rules/ConsultationRules.cs`, `PresetBranch`) checks only that
both lens options belong to `PresetCatalogueId`. It never checks that the catalogue is available
where the record is being created. The availability logic, "assigned to an org whose path is a
prefix of the caller's", exists only in
`PresetCatalogueQueryService.ListAvailableForCallerAsync`.

**Desired behavior:**
- A record whose lens set is retired, or isn't assigned at or above the record's own
  `HierarchyPath`, is rejected with a failure **keyed on `PresetCatalogueId`**. That way the Field
  App's Failed records screen and the Admin Portal conversion form can show it against the
  control. Suggested copy: "This lens set isn't available at this retail point — choose another."
- The location is the one the record will be stamped with:
  - For the three create endpoints, the caller's `HierarchyPathPrefix`.
  - For the Admin Portal's Lead→Sale conversion, the **Lead's** `HierarchyPath`, because the Sale
    inherits the Lead's attribution.
- A converted Lead whose lens set is no longer available carries the set over anyway
  (`SaleAssembly.Seed` is unchanged). This check then flags it and the user picks again. Nothing
  substitutes a set silently.

**Where the check should live — read CLAUDE.md first.** It is a consultation rule, so it
belongs in `DotGlasses.Rules` if the snapshot can answer it. Two constraints:
- Rules may reference only `Contracts`, and must stay I/O-free.
- The App's snapshot is built from the device's cached catalogue list, which the server has
  *already* filtered to the caller's location. A plain "present and active in the snapshot"
  check is therefore correct on the device as it stands. The server snapshot holds every lens
  set, so it additionally needs each set's assigned org paths. The caller's path (a plain
  `string`, since Rules can't see `HierarchyPath`) must also reach `Check`.

If that shape turns out wrong, the fallback is the controller-level, field-keyed pattern CLAUDE.md
describes for `SourceTestId`/`SourceLeadId`. Don't produce a `DomainRuleViolationException`: its
`""` key can't be rendered against a control.

**Acceptance criteria:**
- [ ] API test: creating a Sale (and a Lead, and a Test with a lens set) with a lens set that is
      assigned elsewhere returns 400 with a `PresetCatalogueId` error. The same request from a
      caller under an assigned org succeeds.
- [ ] A retired lens set is refused the same way (once 08 exists; otherwise cover it via the
      snapshot's active flag).
- [ ] Admin Portal conversion of a Lead whose lens set was unassigned from the Lead's location
      re-renders with the error on the lens set field.
- [ ] Rules tests cover assigned-at-an-ancestor (allowed), assigned-at-a-sibling-prefix such as
      `/1/4/` vs `/1/40/` (refused), and not assigned (refused).

**Out of scope:** changing how assignment cascades; the Field App's display filtering (07).
