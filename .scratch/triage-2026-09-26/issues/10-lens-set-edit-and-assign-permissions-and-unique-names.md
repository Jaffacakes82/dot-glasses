# 10 — Lens set editing is limited to the owning org; names are unique among active sets

Status: ready-for-agent
Blocked by: None (touches the Catalogues screen alongside 07/08/11; land after 07 to avoid conflicts)
Category: bug

Source: grilling of ticket 04, 2026-09-26, Joe (Q9, Q10, Q13). See ADR-0005.

## Agent Brief

**Category:** bug

**Summary:** Today any Admin at Country level or above can edit any lens set, including one used
in every country. A Kenya admin can change what Uganda's technicians sell. Editing becomes
limited to the set's owning org. Assigning stays open, within the admin's own scope. Lens set
names must be unique among active sets.

**Current behavior:**
- `CataloguesController` is gated only by `[Authorize(Policy = PresetCatalogueManage)]` (Admin,
  Country level or above). Its actions carry no per-set check. `PresetCatalogue.OwningOrgNodeId`
  is stamped on create from the caller's primary org and never consulted afterwards.
- Names aren't checked for uniqueness.

**Desired behavior:**
- **Edit a lens set.** This covers its name, description, adding or removing lens powers, coating
  availability, and retire/reactivate (ticket 08). It needs the caller to be at or above the set's
  owning org. Reuse the resource-based `HierarchyDescendantRequirement` pattern that
  `Organisations.ManageInScope` / `Users.ManageInScope` use, applied to the owning org's path.
  Resolve that path with `IUnscopedReportQueryService`, because the owning org may sit *above*
  the caller (CLAUDE.md's standing gotcha).
- **Assign / unassign.** Any admin who passes `PresetCatalogue.Manage` may assign **any active**
  lens set, but only **to an org within their own scope**. Unassigning follows the same scope
  rule, applied to the assignment's org.
- **Viewing:** every admin who reaches the screen still sees every lens set. Actions the caller
  can't perform are hidden per set, and the server re-checks regardless (CLAUDE.md: nav filtering
  is never the only guard). A refused POST redirects to Access Denied, as the other policies do.
- **Unique names:** creating or renaming a lens set to a name held by another **active** set is
  refused with a field error on `Name`, compared case-insensitively. Use an async validator
  check in the existing `CreateCatalogueRequestValidator`/`UpdateCatalogueRequestValidator`,
  following the `HasCatalogueWithKindAsync` shape that ticket 07 removes.

**Acceptance criteria:**
- [ ] Web tests: a Kenya-level admin can't edit or add lens powers to a DGI-owned lens set (Access
      Denied), but *can* assign it to a Kenya retail point. A DGI admin can edit it.
- [ ] A Kenya admin can't assign any lens set to a Uganda org.
- [ ] Creating a second active "Reading set", in any letter case, fails on `Name`. Reusing a
      retired set's name succeeds (once 08 exists).
- [ ] Per-set action buttons are hidden where the caller would be refused.
- [ ] CLAUDE.md's RBAC table and `docs/functional-capabilities.md` §4.6 updated.

**Out of scope:** transferring ownership of a lens set; changing who may reach the screen.
