# 05 — CI's migration step authenticates to Postgres by accident (blank username → "runner")

Status: ready-for-human
Blocked by: None
Category: bug (infra / CI)

Source: found during triage of 03, 2026-09-26.

## What's happening

`deploy.yml`'s "Apply database migrations" step builds
`Username=${AZURE_POSTGRES_AAD_USERNAME}`. **That variable is not defined anywhere**: not at
repo level, not on the `staging` or `production` GitHub Environments (`gh variable list`, both
scopes). The staging job log shows `AZURE_POSTGRES_AAD_USERNAME:` blank, so the connection
string carries `Username=;`.

Npgsql then falls back to the OS user of the GitHub runner, which is `runner`. It works only
because `msi-dot-glasses` (principal `c09ce73f-…`) was registered as a nonprod Postgres Entra
admin with the display name **`runner`** (`az postgres flexible-server microsoft-entra-admin
list`). The two coincide, so the Entra token for `msi-dot-glasses` is accepted for user `runner`.

So migrations *do* apply, but through two things that happen to line up, not by design. CLAUDE.md's
Deployment section describes `--display-name` matching the variable "exactly", and the variable
is empty. It breaks silently if:
- GitHub changes the runner's OS username, or the job moves to a runner/container with a
  different user; or
- someone "fixes" the variable to `msi-dot-glasses` without re-registering the Entra admin under
  that name.

Production: not checked. Its Entra admin list should be inspected the same way before the pending
production deploy (still waiting on approval since 2026-09-10) is approved. If prod's admin was
registered under a different name, that deploy's migration step will fail to authenticate.

## Fix (human: needs GitHub settings and Entra admin changes)

1. Pick one display name, e.g. `msi-dot-glasses`. Set `AZURE_POSTGRES_AAD_USERNAME` to it on
   **both** GitHub Environments.
2. Register `msi-dot-glasses` as a Postgres Entra admin under that exact display name on both
   servers (`az postgres flexible-server microsoft-entra-admin create … --display-name
   msi-dot-glasses --object-id <principalId> --type ServicePrincipal`). Remove the `runner` entry
   once the new name is confirmed working.
3. Harden the step: fail fast if the variable is empty, e.g.
   `: "${AZURE_POSTGRES_AAD_USERNAME:?not set}"` after `set -euo pipefail`. That way a blank
   value can never fall back to the OS user again.
