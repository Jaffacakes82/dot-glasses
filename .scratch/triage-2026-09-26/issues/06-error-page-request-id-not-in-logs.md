# 06 — The error page's Request ID can't be found in the logs

Status: done (implemented 2026-09-26, PR #26)
Blocked by: None
Category: bug (observability)

Source: raised by Joe on 2026-09-26 — "The request id that shows on the custom error page doesn't
appear in the logs from what I can see, so it's hard to trace issues."

## Agent Brief

**Category:** bug (observability)

**Summary:** The Admin Portal's error page shows an ID in a format that never appears in any log
line. `HomeController.Error` fills `ErrorViewModel.RequestId` with `Activity.Current?.Id`, which
is the full W3C `traceparent` string: `00-<32-hex trace id>-<16-hex span id>-<flags>`. The
Serilog console sink (`CompactJsonFormatter`, `Program.cs`) writes the trace and span IDs as two
separate fields, `@tr` and `@sp`. The only field it writes named `RequestId` holds a different ID
entirely: `HttpContext.TraceIdentifier`, taken from ASP.NET Core's hosting log scope. So pasting
the ID from the page into a log search finds nothing, even though the unhandled-exception line
*is* logged at Error level on the same request.

**Verified 2026-09-26** with a scratch program on the same Serilog versions as `Web`
(Serilog 4.3.0, Serilog.Formatting.Compact 3.0.0):

```
log line:   "@tr":"35272347c579ddf9d562af853e863f5a","@sp":"97ada7fe33706b78","RequestId":"0HNABC123:00000001"
page shows: 00-35272347c579ddf9d562af853e863f5a-97ada7fe33706b78-00
```

**Workaround until fixed:** search the logs for the 32-hex middle segment only, e.g.
`ContainerAppConsoleLogs_CL | where Log_s has "<trace id>"`.

**Current behavior:** the error page shows `Request ID: 00-<trace>-<span>-<flags>`, which matches
no log field verbatim.

**Desired behavior:** the error page shows the request's **trace ID**: the 32-hex value that
appears as `@tr` on every log line written during that request. It is labelled "Trace ID". The
same value will be the operation ID in Application Insights once an exporter is wired (see
`docs/open-issues.md`), so this is the one ID worth surfacing. If there's no W3C activity (not
expected in practice, since ASP.NET Core creates one per request whenever OpenTelemetry is
listening), fall back to `HttpContext.TraceIdentifier`, which at least matches the `RequestId`
log property.

**Key interfaces:**
- `src/DotGlasses.Web/Controllers/HomeController.cs` — `Error()` builds the ID.
- `src/DotGlasses.Web/Models/ErrorViewModel.cs` — rename `RequestId`/`ShowRequestId` to
  `TraceId`/`ShowTraceId`.
- `src/DotGlasses.Web/Views/Shared/Error.cshtml` — label and binding.

**Acceptance criteria:**
- [ ] With a W3C `Activity` current, `Error()` returns a model whose ID equals
      `Activity.TraceId.ToHexString()`, the value Serilog writes as `@tr`.
- [ ] With no current `Activity`, it falls back to `HttpContext.TraceIdentifier`.
- [ ] The page labels the value "Trace ID".
- [ ] Unit tests in `DotGlasses.Web.Tests` pin both cases (no container needed).

**Out of scope:**
- Wiring an OTLP/Azure Monitor exporter (tracked in `docs/open-issues.md`).
- Adding Serilog request logging or changing log levels/content.
- The Field App's own error UI.
